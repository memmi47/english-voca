# C-007 저장 형식 3·회오리·기록 보호 교차 검토

검토자: Codex Astra. 날짜: 2026-11-17. 기준: `b44e85a98c445dced38b3ce576768c4c3809781b` (`claude/modest-mccarthy-3gadjk`). 아래 소스 줄은 이 커밋 기준이다. 게임 코드·검사·자료·저장 fixture는 바꾸지 않았다. 실제 아이의 기록이나 외부 백업 저장소를 사용하지 않았다.

**판정: 검토 완료, 기록 보호 결함 4건을 수정 카드로 넘긴다.** 심각도별로 **기록 손실/손실 위험 3건(R1~R3), 진행 막힘 0건, 규칙 위반 1건(R4), 사소함 0건**이다. 시계 오차는 T-011이 이미 남겨 둔 설계 한계로 별도 재현했으며 새 결함 수에 더하지 않았다. 필수 검사 단위 **100/100**, 브라우저 **153/153**, 시뮬레이션 기준 비교는 모두 통과했다.

가장 중요한 R1은 화면이 새 형식을 감지해 이미 읽기 전용이 됐는데도, 늦게 끝난 동기화가 그 새 저장을 구형 사본으로 덮어쓰는 경로다. Chromium 두 탭에서 같은 형식의 단어·형태 기록 손실과 **형식 4→3**을 재현했고, 보관된 실제 형식 2 모듈로 **형식 3→2**도 재현했다.

## 1. 발견 사항 — 심각도 순

### R1. 기록 손실 — 응답 본문을 기다리던 동기화가 다른 탭의 새 기록을 덮어쓴다

- **실제 재현:** 현행 `Sync` + Chromium 두 탭, 실제 `storage` 이벤트. HTTP 응답의 헤더와 JSON 본문 완료 사이를 제어한 응답 대역을 사용했다. 별도로 Node에서 실제 과거 커밋 `5a09449`의 형식 2 `deck.js`·`store.js`·`sync.js`로 같은 순서를 실행했다. 전체 구형 화면을 기동한 실험은 아니다.
- **상태·순서:** A가 `p.son`의 이전 로컬 값을 가진 상태에서 `reconcile('p.son')`을 시작한다. GET 응답의 `json()`을 대기시킨다. 같은 origin의 B가 `words.tabB`, `forms.onlyB`를 추가해 저장한다. 같은 형식 3인 경우와 더 새 형식 4인 경우를 각각 실행한다. A의 `storage` 이벤트가 처리되어 같은 형식은 메모리에 합쳐지고, 새 형식은 `readonly=true`가 된 것을 확인한 뒤 이전 서버 본문을 반환한다.
- **관측:** 두 경우 모두 로컬의 `tabB`와 `onlyB`가 사라졌다. 같은 형식은 `v=3, readonly=false, stale=false`, 새 형식은 **`v=3, readonly=true, stale=false`**였다. 읽기 전용 표시가 동기화 쓰기를 막지 못했다. 과거 형식 2 모듈에서도 `v=3`·새 단어·`forms`가 **`v=2`·빈 단어·forms 없음**으로 바뀌었다.
- **원인·근거:** [`sync.js:154`](../../cards/js/sync.js#L154)가 로컬을 읽고 형식을 검사한 뒤 [`sync.js:158`](../../cards/js/sync.js#L158)의 `await r.json()`을 지난다. [`sync.js:160`](../../cards/js/sync.js#L160) 또는 [`sync.js:162`](../../cards/js/sync.js#L162)는 그 사이 바뀐 현재 로컬을 다시 읽지 않고 이전 값으로 교체/병합한다. [`main.js:50`](../../cards/js/main.js#L50)의 읽기 전용과 [`main.js:54`](../../cards/js/main.js#L54)의 저장 가드는 이 직접 쓰기에 참여하지 않는다. `onMerged`도 [`main.js:61`](../../cards/js/main.js#L61)에서 그 결과를 그대로 메모리에 반영한다. DATA_SAFETY의 [다른 탭 보호 약속](../DATA_SAFETY.md#L23)이 지켜지지 않는다.
- **서버 방어의 한계:** 서버는 이미 보관한 형식보다 낮은 PUT을 거부하지만, B가 아직 서버에 올리지 않은 로컬 전용 단어·형태는 서버에 없다. 같은 단어 수인 형태 손실도 축소 검사 대상이 아니다. 따라서 서버의 버전 거부만으로 이 손실을 복원할 수 없다.
- **고치는 방향:** 원격 본문을 모두 받은 뒤 쓰기 직전에 로컬을 다시 읽고 새 형식 차단 및 최신 로컬과의 병합을 수행한다.

### R2. 기록 손실 — 손상 원문 사본을 만들 수 없는데도 원문을 교체한다

- **실제 재현:** 메모리 저장소 대역과 Chromium의 실제 `localStorage` 용량 제한 양쪽에서 확인했다. 실제 브라우저에서는 `p.son`에 `{"v":3,"words":{"localOnly":`로 시작하는 **3,145,756문자**의 읽을 수 없는 값을 넣었다. 같은 크기의 두 번째 값을 추가하면 실제 `QuotaExceededError`가 발생하지만 작은 값으로 원래 키를 교체할 수 있는 상태다.
- **상태·순서:** 위 로컬 값과 작은 정상 서버 기록을 두고 `Sync.reconcile('p.son')`을 실행한다. 별도 대역에서는 `loadRecord` 뒤 호출자의 저장도 실행했다.
- **관측:** 동기화 뒤 원래 키는 **107문자**의 서버 기록으로 바뀌고 **`.damaged.` 사본은 0개**였다. 기존 텍스트의 로컬 전용 내용을 조사·수동 복구할 수 있는 원문을 잃는다. 정상 단어 기록을 읽어 줄 수 있었다는 뜻은 아니며, 보관하겠다고 약속한 손상 원문의 손실이다.
- **원인·근거:** [`store.js:59`](../../cards/js/store.js#L59)의 `setAside`는 실패하면 `false`를 돌려주지만 [`sync.js:133`](../../cards/js/sync.js#L133)이 이를 무시하고 “로컬 없음”을 반환한다. 이후 [`sync.js:160`](../../cards/js/sync.js#L160)이 서버 기록을 쓴다. [`store.js:73`](../../cards/js/store.js#L73)의 `loadRecord`와 [`main.js:48`](../../cards/js/main.js#L48)의 저장 전 보관도 같은 반환값을 무시한다. DATA_SAFETY의 [먼저 보관한 뒤 복구](../DATA_SAFETY.md#L24) 약속과 어긋난다. 기존 D4의 용량 실패 검사는 예외가 밖으로 나오지 않는지만 확인하고, 후속 교체에 의한 원문 손실은 검사하지 않는다.
- **고치는 방향:** 보관 실패를 호출자까지 전달해 해당 키의 쓰기를 멈추고, 원문 내보내기 또는 보관 성공 후에만 교체한다.

### R3. 기록 손실 위험 — 다른 ref만 push해도 새 백업 커밋을 올렸다고 기록한다

- **실제 재현:** 실제 Git·백업 스크립트, 임시 작업 저장소와 로컬 bare 저장소. 네트워크·실제 아이 자료 없음. 기본 clone에 없는 **사용자 지정 push refspec**이 필요한 조건이다.
- **상태·순서:** `main`의 최초 커밋을 origin에 올린다. 그 커밋을 가리키는 `archive` 브랜치를 만들고 `git config remote.origin.push archive:archive`를 설정한다. 합성 `p.son.json`을 백업한다. 스크립트는 `main`에 새 백업 커밋을 만들지만 인수 없는 `git push -q`는 지정된 `archive`만 보낸다.
- **관측:** 종료 **0**, “백업 완료”, **`offsite.ok=true`**, `offsite.commit=<새 main 커밋>`이 기록됐다. 원격 `main`은 최초 커밋이고, 원격에서 `git cat-file -e <새 백업 커밋>`은 실패했다. 실제로는 새 백업 커밋 자체가 원격에 없다. 로컬 기록은 남지만 Mac 저장소를 잃으면 “올림”으로 표시된 사본으로 복구할 수 없다.
- **원인·근거:** [`backup_state.sh:73`](../../tools/backup_state.sh#L73)은 현재 브랜치에 커밋하지만 [`backup_state.sh:74`](../../tools/backup_state.sh#L74)의 push는 목적 ref를 지정하지 않는다. [`backup_state.sh:75`](../../tools/backup_state.sh#L75)는 현재 HEAD가 도착했는지 확인하지 않고 성공을 적는다. “변경 없음” 경로의 [`backup_state.sh:70`](../../tools/backup_state.sh#L70)도 같다. T-011 F4의 “push 명령 실패를 성공으로 쓰는” 원래 결함은 고쳐졌지만 **명령 성공과 이번 백업의 원격 보관은 같지 않다.**
- **고치는 방향:** 검증한 원격의 명시적 백업 ref에 현재 백업 커밋을 올리고, 그 ref가 해당 커밋을 가리키는지 확인한 뒤 성공을 기록한다.

### R4. 규칙 위반 — 검증한 origin 한 주소와 실제 push 대상이 다를 수 있다

- **실제 재현:** 서로 다른 로컬 bare 저장소 두 개로 검증 대상과 실제 수신 대상을 구분했다. 공개 GitHub 주소 형태는 `url.<임시 bare>.insteadOf`로 반드시 로컬에만 연결했다. 실제 공개 GitHub 업로드는 하지 않았으며, **공개 노출 위험은 이 검증 우회의 결과로 추론**한다. 기본 clone에는 없는 설정이 필요한 조건이다.
- **상태·순서 A:** origin은 허용되는 로컬 `checked.git`이다. 별도 remote `publish`에 `https://github.com/c007-audit/public.git`을 두고 `branch.main.pushRemote=publish`를 설정한다. 응답 대역은 `CARDS_BACKUP_TEST_HTTP=200`으로 둔다. 해당 주소가 검사됐다면 공개로 거부되어야 한다.
- **상태·순서 B:** origin에 pushurl을 두 개 넣는다. 첫 주소는 위 GitHub 형태, 마지막 주소는 허용되는 로컬 `checked.git`이다. `git config --get remote.origin.pushurl`은 마지막 값만 돌려주지만 `git push origin`은 설정된 여러 push 주소로 전송한다.
- **관측:** A·B 모두 종료 **0**, `offsite.ok=true`였고 **검사하지 않은 두 번째 저장소에 `state-cards/p.son.json`과 백업 커밋이 실제로 도착**했다. 공개 응답 200 거부 분기는 실행되지 않았다.
- **원인·근거:** [`backup_state.sh:36`](../../tools/backup_state.sh#L36)은 raw origin URL 하나만 읽는다. 실제 [`backup_state.sh:70`](../../tools/backup_state.sh#L70)·[`backup_state.sh:74`](../../tools/backup_state.sh#L74)는 원격을 명시하지 않아 `branch.*.pushRemote` 등의 설정을 따른다. 복수 pushurl과 URL 재작성도 검증한 문자열과 최종 목적지를 다르게 만들 수 있다. DATA_SAFETY [3절](../DATA_SAFETY.md#L41)의 비공개 대상 검증보다 실제 보장이 좁다.
- **고치는 방향:** 실제 전송될 최종 push URL 전체와 remote를 확정·검증하고, 검증한 대상에만 명시적으로 push한다.

## 2. 시계와 병합에서 확인한 설계 한계 — 새 결함 수에 포함하지 않음

**시계 오차/역행: 실제 모듈 재현.** 먼저 정답을 기록한 기기의 시계가 5분 빠르다고 두었다. 먼저 저장한 단어는 `done, due:null, at=10:05`, 형태는 `n:2, ok:2, at=10:05`다. 그 상태를 받은 정상 시계 기기(또는 시계를 바로잡은 같은 기기)가 실제로 나중인 10:01에 오답을 기록해 단어 `learn, due=다음 날, at=10:01`, 형태 `n:3, ok:0, at=10:01`을 만든다. 양방향 `mergeCards` 모두 먼저 답한 **done / ok:2**를 택해 후속 오답·재학습 일정이 상태에서 빠졌다.

[`deck.js:202`](../../cards/js/deck.js#L202)·[`storm.js:39`](../../cards/js/storm.js#L39)는 기기 시각을 그대로 쓰고, [`sync.js:17`](../../cards/js/sync.js#L17)·[`sync.js:73`](../../cards/js/sync.js#L73)은 큰 `at`을 택한다. 이는 T-011이 정한 비교 규칙대로이며 [T-011 설계 검토](../tasks/T-011.md#L172)에 이미 남긴 한계다. 잘못된 시계로 실제 답변 순서를 알 수 있다고 주장하지 않는다. `here`·`storm`도 [`sync.js:101`](../../cards/js/sync.js#L101)의 최대 `endedAt` 선택에 의존하므로 같은 제약이 있다(지도까지의 영향은 소스 판독). 수정하려면 인과/기기별 버전 또는 관측한 기존 시각보다 뒤인 논리 시각을 별도 설계해야 한다. 서로를 못 본 동시 변경의 정책도 필요하다.

그 밖에 `compact` 후 **30일보다 오래 떨어져 플레이한 다른 기기의 판 통계가 빠질 수 있는 한계**는 DATA_SAFETY 2절과 T-011이 이미 명시한 범위다. 이번 D5·F2는 최근 501판에 다른 기기 1판을 합치면 502판을 유지하고, 오래된 동일 이력은 합계가 유지되는 것을 다시 통과했다. 이를 장기 오프라인 이력의 무손실 보장으로 해석하지 않는다. 별·아이템의 양쪽 획득량을 더하지 않고 큰 값만 택하는 [`sync.js:24`](../../cards/js/sync.js#L24)의 기존 정책도 보존했다.
