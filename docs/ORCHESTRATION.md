# 작업 운영 방식 (초안, 검증 대상)

작성 2026-11-16. 상태: 적용 중. 사용자 결정(2026-11-16): 자동 검사 도입, 병합 충돌은 Claude가 해결, Codex 작업은 카드와 프롬프트(`docs/tasks/CODEX_PROMPT.md`)로 할당. 교차 검토 범위(6절 3번)는 추천안(민감한 PR만)으로 잠정 운영. 목적: 상위 모델이 전체 그림과 명세를 만들고, 사용자가 검증하고, 구현은 모델별로 나눠 맡기되 중간에 같은 기준으로 점검한다.

## 1. 역할

| 층 | Claude | Codex | 맡는 일 | 맡기지 않는 일 |
|---|---|---|---|---|
| 설계·판정 | Fable | Astra | 명세, 규칙·수치 결정, 시뮬레이션, 작업 카드 작성, 상대편 PR 검토, 실패 원인 판정 | 반복 구현 |
| 구현 | Opus | Sol | 명세가 확정된 기능과 그 테스트, 하위 층 결과 검토 | 규칙·저장 형식·자료 계약을 바꾸는 결정 |
| 실행 | Sonnet | Terra | 자료 생성, 문서·문구, 반복 수정, 테스트 보강 | 여러 파일에 걸친 설계 변경 |

- 분야는 지금처럼 나눈다. Claude 쪽: 게임 규칙·화면·저장·테스트. Codex 쪽: 세계·단어 자료·생성기·도안.
- 사용자: 목적과 우선순위, 명세 승인, 기기 확인, PR 병합.
- 층을 올리는 기준: 완료 기준 테스트를 두 번 고쳐도 통과하지 못하면 한 층 위로 올린다. 카드에 없는 결정이 필요해지면 멈추고 설계 층에 묻는다. 추측으로 채우지 않는다.
- 최고 노력 모드("울트라")는 두 곳에서만 요청한다: 명세 확정 전 검토, 저장 형식·복습 규칙을 건드리는 PR의 교차 검토.

## 2. 흐름과 점검 지점

```
목표(사용자) → 명세(설계 층) → [점검 A: 사용자 승인] → 작업 카드 → 구현(구현·실행 층)
  → [점검 B: 자동 검사] → [점검 C: 교차 검토] → [점검 D: 기기 확인] → 병합(사용자)
```

| 점검 | 누가 | 무엇을 | 통과 기준 |
|---|---|---|---|
| A 명세 | 사용자 + 설계 층 | 명세 문서의 항목별 승인·수정·보류 | 승인된 항목만 카드가 된다 |
| B 자동 | 기계 | 단위·브라우저 테스트, 저장 호환(`cards_safety`), 자료 불변(4,610장 누락·중복 0, 세계 파일 버전), 규칙을 건드렸으면 시뮬레이션 회귀 | 전부 통과. 실패한 채로 다음 카드로 넘어가지 않는다 |
| C 교차 | 상대편 설계 층 | Claude의 PR은 Astra가, Codex의 PR은 Fable이 읽는다. 카드의 완료 기준과 "바꾸면 안 되는 것"을 기준으로 | 지적 사항이 해결되거나 사용자에게 올라간다 |
| D 기기 | 사용자 | iPad·맥미니에서 카드의 확인 목록대로 | 사용자가 병합한다 |

- 점검 B는 `.github/workflows/tests.yml`이 PR마다 자동으로 돌린다(단위, 저장 호환 자료, 세계 자료 검사, 브라우저). 규칙 회귀(시뮬레이션 출력 비교, `tools/check_sim_baseline.mjs`)도 함께 돈다. 규칙을 일부러 바꾼 PR은 `node tools/check_sim_baseline.mjs --update`로 기준 파일(`tests/fixtures/sim/chosen-seeds2.txt`)을 고치고, PR 설명에 무엇이 왜 달라졌는지 적는다.
- 주기: 카드 하나가 끝날 때마다 B, 묶음(관련 카드 3~5개)이 끝날 때마다 C와 D.

## 3. 작업 카드

- 위치: `docs/tasks/`. 양식: `docs/tasks/TEMPLATE.md`. 카드 하나가 PR 하나다.
- 카드만 읽고 일할 수 있어야 한다. 이 대화의 맥락에 기대는 문장을 쓰지 않는다.
- 카드에 반드시 있는 것: 목표(한 문장), 배경 문서 링크, 고칠 수 있는 파일, 바꾸면 안 되는 것, 완료 기준(실행할 명령과 기대 결과), 담당 층, 선행 카드, 사용자 확인 목록.
- `docs/WORKLOG.md`의 역할은 줄인다: 현재 상태, 결정 기록, 이력. 계획과 요청은 카드로 옮긴다.

## 4. 자동 검사 (제안)

| 검사 | 명령 | 언제 |
|---|---|---|
| 단위 | `node --test tests/*.test.mjs` | 모든 PR |
| 브라우저 | `node tests/cards_e2e.cjs` | 모든 PR |
| 자료 | `python3 -I tools/make_cards_data.py` 후 변경 없음, 세계 생성기의 `--check` | 자료·생성기 PR |
| 규칙 회귀 | `node tools/sim_learning.mjs --set chosen --seeds 3` 결과가 기준값(54주, 79%)에서 ±10% 안 | `deck.js`·`map.js`·`world.js`를 고친 PR |
| 저장 호환 | `tests/fixtures/saves/`의 파일이 줄지 않았는지, `cards_safety` 통과 | 모든 PR |

## 5. 멀티에이전트로 돌리는 방법

- Claude 쪽: 설계 층 세션이 카드를 쓰고, 카드마다 하위 모델 작업자를 띄워 구현시키고, 결과를 점검 B로 확인한 뒤 PR로 올린다. 서로 다른 파일을 고치는 카드는 동시에 진행할 수 있다. 같은 파일을 고치는 카드는 순서대로 한다.
- Codex 쪽: 같은 카드 양식을 쓴다. Claude 세션이 Codex를 직접 실행할 수는 없으므로 접점은 카드와 PR이다.
- 두 쪽이 같은 파일을 고쳐야 하면 카드를 쪼개 한쪽이 먼저 병합된 뒤 다른 쪽이 시작한다. 지금까지의 충돌은 `docs/WORKLOG.md` 하나였고, 계획·요청을 카드로 옮기면 그 충돌이 준다.
- 비용: 설계 층은 명세·판정·검토에만 쓴다. 카드의 "담당 층"이 기본값이고, 올리는 기준(1절)에 걸릴 때만 위층을 쓴다.

## 6. 사용자가 정할 것

1. 이 역할표와 점검 지점으로 진행해도 되는가.
2. GitHub Actions 자동 검사를 넣어도 되는가(저장소에 `.github/workflows/` 파일이 생긴다).
3. 교차 검토(점검 C)를 모든 PR에 할지, 저장 형식·복습 규칙·자료 계약을 건드리는 PR에만 할지. 추천은 뒤쪽이다.
